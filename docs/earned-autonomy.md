# Earned Autonomy — 実績で獲得する自律 (design)

## 解いている矛盾

この製品の前提は「深夜 2 時、オンコール要員はいない」。しかし復旧ループの真ん中には
人間の承認クリックがある。承認ゲートは安全の根拠であると同時に、**MTTR の下限を
人間の睡眠時間で縛る**。ゲートを外せば安全の主張が消え、残せば前提と矛盾する。

答えは「外す/残す」の二択ではない: **ゲートを、自分の実績で自分を狭めていく
動的な信頼境界にする**。

## 仕組み (3 部品)

### 1. 信頼台帳 (trust ledger) — `agents/autonomy.py` + `GET /trust`

人間が承認した修復の結果は、以前から全件記録されている
(`case_store.record_resolution`: 復旧検証が実際に 200 を返したか)。これを
修復クラス (どの env var を復元したか) ごとに集計し、**検証済み成功率の
Wilson 下限**を出す。

- 下限が閾値 (default 0.80) を超えたクラスだけ「昇格」= 自律実行可
- 生の成功率ではなく下限を使う理由: 3/3 (下限 ~0.44) がまぐれで開けてはいけない。
  16/16 (~0.81) の証拠量が要る。**ゲートは運では開かず、実績量で開く**
- 台帳は読み取り専用の報告であり、昇格前から `GET /trust` で常時公開される —
  「ゲートの引退スケジュール」を先に見せる
- 端末から読むなら `autosre status` (1 回) / `autosre watch` (常駐画面)。watch は
  下限と閾値をバーで並べ、未昇格クラスには**あと何回の検証済み復旧で昇格するか**を
  出す — 引退スケジュールを「回数」で言い切る

### 2. ゼロトラフィック・リハーサル — `recovery.rehearse_env_fix`

自律実行は、直す前に**証明**する。修正済み構成を Cloud Run の新 revision として
デプロイするが、トラフィックは現行 revision に 100% ピンしたまま (=ユーザー影響ゼロ)。
新 revision は `rehearsal` タグの URL でヘルスチェックされ、**緑になって初めて**
merge + トラフィック切替に進む。

- 昇格 = トラフィックを LATEST 100% に戻すだけ (ビルド不要、瞬時)
- 巻き戻し = 旧 revision に 100% ピン (同じく瞬時) — **これが可逆性の根拠**
- リハーサルが赤なら何も動かさない: serving revision は無傷、PR は従来どおり
  人間の承認待ちに落ちる (fail-closed)

### 3. 一発降格 (one-strike demotion) — `state_store.set_demotion`

自律実行後の本検証が失敗したら:

1. トラフィックを即座に旧 revision へ巻き戻す
2. 失敗を**同じ台帳に記録する** (昇格を支えた統計は失敗も数える)
3. そのクラスを**即降格** — GCS 状態オブジェクトに CAS で永続化
4. 降格からの復帰は `POST /trust/rearm` (人間) のみ。**統計は初回の昇格しか
   開けない。一度打たれた後は、人が見るまで二度と開かない**

## 昇格しても残るもの

- 日次実行上限と kill switch (外周のコスト境界)
- 修復 allowlist (`AUTOSRE_ALLOWED_ENV_VARS` 外は永久にゲートの中)
- escalate クラス (エージェント自身が範囲外と判断したもの)
- 監査記録 (自律実行は audit dict として応答・SSE・ログに全量残る)

人間の仕事が消えるのではなく、**「提案の審査」から「実績の監査」へ移動する**。

## 設定 (default-off の段階導入、他の AUTOSRE_* と同じ契約)

| env | 意味 |
|---|---|
| `AUTOSRE_AUTONOMY_ENABLED` | 未設定 = 自律実行なし。台帳の閲覧だけは常時可 |
| `AUTOSRE_AUTONOMY_THRESHOLD` | 昇格に必要な Wilson 下限 (default 0.80) |

診断パス (`agents/agent.py`) には一切触れていない — 診断精度の実測 eval は
この機能の前後で同一。変わるのは診断の**後**、ゲートの層だけ。
